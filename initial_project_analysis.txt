3. BACKEND STATUS
--------------------------------------------------------------------------------

Server (server.js)
------------------
  JSON body parser, CORS for http://localhost:5173 and 5174, request logging
  Listens on PORT 5000
  Mounts /api/auth, /api/items

Routes
------
  routes/authRoutes.js  — POST /register, POST /login
  routes/itemRoutes.js  — GET/POST /, GET/PATCH/DELETE /:id

Controllers
-----------
  controllers/authController.js  — register/login (see auth below)
  controllers/itemController.js  — list (optional ?status= mapped to type),
                                   get by id, create, patch status, delete

Models
------
  models/Item.js — full item schema with type (lost|found),
                   status (pending|resolved), is_resolved,
                   postedBy as ObjectId ref to 'User'

MongoDB connection
------------------
  Connects when MONGO_URI is set; on failure logs and process.exit(1) —
  correct pattern, but no .env in repo (expected; .gitignore ignores .env).
  You must create server/.env locally.

Authentication
----------------
  Register: returns only { message: 'User registered' } — does not create
            a user, hash a password, or return token / user.

  Login:    returns fixed token: 'mock-jwt-token' and fixed user
            (_id always 507f1f77bcf86cd799439011, name "Test User",
            email from body or default). Password is ignored.

  bcryptjs and jsonwebtoken are installed but NOT used in authController.js.

  No auth middleware on item routes; JWT is never verified; no ownership
  checks on PATCH/DELETE (anyone who can call the API could act on any item id).

APIs (purpose)
--------------
  POST   /api/auth/register     Intended registration (currently stub)
  POST   /api/auth/login        Intended login (currently mock token/user)
  GET    /api/items             List items; ?status=lost|found filters by type
  GET    /api/items/:id         Single item
  POST   /api/items             Create item (requires body fields incl. postedBy)
  PATCH  /api/items/:id         Set status (e.g. resolved) and is_resolved
  DELETE /api/items/:id         Delete item
  GET    /                      Health: "API Running"

6. BUGS / ERRORS / MISMATCHES
--------------------------------------------------------------------------------

TypeScript (npm run typecheck) — fails
--------------------------------------
  1) Navbar.tsx: user_metadata not on User type.
  2) dummy.ts: multiple errors (status used where Item expects type as
     lost|found, etc.).

Auth / API contract
-------------------
  • Register: backend does NOT return token / user; frontend signUp
    destructures them → runtime failure after HTTP 201 unless one side changes.

Security / logic
----------------
  • Item delete/update not restricted to poster on the server.
  • Owner UI on ItemDetails compares user?._id === item.postedBy; JSON usually
    stringifies postedBy correctly; server-side check matters for submission.

Environment
-----------
  • Server: requires MONGO_URI (no sample file in repo).
  • Client: hardcoded API URL — fine for local demo, brittle for deployment.
  • Supabase: if anything imported supabase.ts without env vars, client would
    misconfigure — currently unused.

Dependencies / metadata
-----------------------
  • server/package.json has "main": "index.js" but app is server.js —
    harmless if you always nodemon server.js.
